# RF-15

# Contexto y Objetivo
Optimizar y estandarizar el despliegue en Docker y Docker Compose para todo el ecosistema **`JettraStore`**, **`JettraStoreShell`** y **`JettraStoreExplorer`**, configurando cada `Dockerfile` y archivo Compose para un consumo reducido de recursos (RAM, CPU y disco), garantizando persistencia independiente por nodo (con volúmenes en storage permanente), validando el consenso Raft y la conmutación por error (failover) de `PRIMARY` a `SECONDARY`, y actualizando **`/guide/book.md`** en cada proyecto.

# Tareas Requeridas

## 1. Configuración de Dockerfiles para Bajo Consumo de Recursos (`JettraStore`, `JettraStoreShell`, `JettraStoreExplorer`)
- Configurar los `Dockerfile` de **`JettraStore`**, **`JettraStoreShell`** y **`JettraStoreExplorer`** específicamente para bajo consumo de recursos:
  - Usar imágenes base ligeras (por ejemplo, Alpaquita Linux / Alpine o imagen mínima compatible con Java 25+) y build multi-etapa eliminando cachés y dependencias innecesarias.
  - Definir variables de entorno y `JAVA_TOOL_OPTIONS` / flags de JVM en Java 25+ orientadas a bajo footprint de memoria y arranque eficiente (ajustando heap/metaspace, GC y compatibilidad con arenas off-heap / Project Panama FFM y almacenamiento slotted-page `.jettra` en `JettraStore`).
  - Configurar directorios de trabajo, archivos de configuración (`src/main/resources/cluster.config`, `src/main/resources/META-INF/microprofile-config.properties`) y rutas de storage persistente preparadas para montarse como volúmenes independientes por instancia.
- Probar la construcción de las imágenes desde sus respectivos `Dockerfile` (`JettraStore`, `JettraStoreShell` y `JettraStoreExplorer`) y su publicación/actualización en Docker Hub.

## 2. Docker Compose Multi-Nodo (3 Nodos de `JettraStore` + `JettraStoreShell` + `JettraStoreExplorer`)
- Actualizar el `docker-compose.yml` multi-nodo integrando los 3 nodos de **`JettraStore`** junto con **`JettraStoreShell`** y **`JettraStoreExplorer`**, aplicando en todos los servicios las optimizaciones de bajo consumo de memoria y CPU (incluyendo límites de memoria y recursos por contenedor).
- Asignar a cada nodo de `JettraStore` su propio directorio de almacenamiento persistente (`.jettra` / datos del nodo) mediante volúmenes dedicados para que detener, recrear o restaurar un nodo conserve su storage de forma permanente sin colisiones.
- Configurar correctamente la red interna Docker y el descubrimiento de nodos para que `JettraStoreShell` y `JettraStoreExplorer` se conecten al clúster de 3 nodos y reflejen en tiempo real el estado de los nodos (`PRIMARY` / `SECONDARY`).

## 3. Docker Compose de un Solo Nodo (`JettraStore` + `JettraStoreShell` + `JettraStoreExplorer`)
- Crear archivos Docker Compose independientes para despliegue de un solo nodo (`docker-compose-single-node.yml` o equivalente documentado) configurados con las mismas optimizaciones de bajo consumo de recursos, storage persistente permanente para `JettraStore` y conexión operativa para `JettraStoreShell` y `JettraStoreExplorer`.

## 4. Pruebas de Consenso Raft, Failover y Operación en Shell/Explorer
- Levantar las 3 instancias de `JettraStore` (junto con `JettraStoreShell` y `JettraStoreExplorer`) mediante Docker Compose y verificar que el clúster elija **1 nodo `PRIMARY` y 2 nodos `SECONDARY`**.
- Comprobar el funcionamiento del algoritmo Raft (replicación de estado/operaciones entre `PRIMARY` y `SECONDARY` y persistencia en cada storage).
- Verificar desde `JettraStoreShell` (`show nodes`, consultas y operaciones) y desde `JettraStoreExplorer` (`/cluster` y `/explorer`) la correcta detección del rol `PRIMARY` y los `SECONDARY`.
- Detener el contenedor del nodo `PRIMARY` y verificar que uno de los nodos `SECONDARY` asuma automáticamente el rol de `PRIMARY` sin pérdida de datos persistidos, y que tanto `JettraStoreShell` como `JettraStoreExplorer` actualicen el nuevo `PRIMARY`.
- Volver a iniciar el nodo detenido y verificar su reincorporación limpia al clúster y la consistencia del storage.

## 5. Pruebas Automatizadas y Actualización de `/guide/book.md` en Cada Proyecto
- Añadir pruebas con `JettraTest` en `JettraStore`, `JettraStoreShell` y `JettraStoreExplorer` que cubran la validación del ciclo de vida/consistencia de almacenamiento, reconexión y failover esperado en el clúster.
- Actualizar de forma obligatoria el archivo **`/guide/book.md`** de cada proyecto (**`JettraStore/guide/book.md`**, **`JettraStoreShell/guide/book.md`** y **`JettraStoreExplorer/guide/book.md`**) documentando:
  - Configuración de cada `Dockerfile` para consumo reducido de recursos.
  - Despliegue de 1 nodo y de 3 nodos con storage persistente independiente.
  - Procedimiento y verificación de consenso Raft, caída/promoción de `PRIMARY` y monitoreo desde `Shell` y `Explorer`.
  - Flujo de compilación, prueba y publicación de las imágenes en Docker Hub.

# Criterios de Aceptación
- Los `Dockerfile` de `JettraStore`, `JettraStoreShell` y `JettraStoreExplorer` generan imágenes compactas configuradas para bajo consumo de recursos, publicadas y verificadas en Docker Hub.
- El clúster de 3 nodos arranca con 1 `PRIMARY` y 2 `SECONDARY` con huella reducida de memoria, storage persistente independiente por nodo y conectividad plena desde `JettraStoreShell` y `JettraStoreExplorer`.
- Al detener el `PRIMARY`, un `SECONDARY` toma el rol `PRIMARY`, los datos permanecen intactos en el storage y ambos clientes (`Shell` y `Explorer`) reflejan el cambio.
- Los despliegues de 1 nodo funcionan de forma autónoma y los archivos `/guide/book.md` de `JettraStore`, `JettraStoreShell` y `JettraStoreExplorer` están actualizados con ejemplos ejecutables.
