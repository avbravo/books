# Progreso


**Contexto del Proyecto:**
Estamos trabajando en el ecosistema **Jettra**, cuyo proyecto principal de base de datos se llama **JettraStore**, complementado por sus módulos y clientes (`JettraPolice`, `JettraStoreDriver`, `JettraShell`, `JettraStoreFX`). Necesitamos refinar el mecanismo de protección Anti-OOM de `JettraPolice` en **JettraStore** para que gestione consultas masivas o sobre toda la base de datos de forma automática, segura y totalmente transparente para el código de negocio del cliente (ej. `findAll()`, `select * from ...` o consultas mediante `JettraQL`).

**Objetivo Principal:**
Implementar un protocolo de comunicación basado en **Streaming por Chunks + Metadatos de Notificación**, donde el servidor procese los datos en bloques seguros (liberando memoria iterativamente) y el cliente reciba un flujo continuo que garantice el rendimiento tanto en el servidor como en el cliente, permitiendo notificar a las interfaces gráficas o de consola cuando el Sentinel de `JettraPolice` sea activado.

**Requerimientos de Implementación:**

1. **Estructura de Metadatos y Notificación (Sentinel):**
* Diseñar un mecanismo o envoltorio de metadatos (`JettraPoliceNotification`) que capture cuándo se activa la paginación lazy anti-OOM (incluyendo tamaño del lote seguro, total de registros estimados, estado del Heap y mensajes de advertencia).
* Proveer un sistema de eventos o listeners (`JettraPoliceEventListener`) en el driver (`JettraStoreDriver`) para que, de forma completamente desacoplada, cualquier cliente (`JettraShell` o `JettraStoreFX`) se entere de que la paginación automática ha sido forzada, permitiendo mostrar feedback visual o en consola al usuario sin alterar las firmas de los métodos del cliente.


2. **Procesamiento y Streaming en Servidor (`JettraStore`):**
* El motor de **JettraStore** debe procesar las consultas masivas particionándolas en lotes seguros (ej. 100 registros por lote).
* Cada lote debe procesarse en un área de memoria libre, vaciando referencias y facilitando la recolección de basura (*Garbage Collection*) entre lote y lote.
* Los datos deben ser devueltos mediante un flujo continuo tipo stream (`StreamResponse`), evitando cargar todo el resultado de golpe en la memoria RAM del servidor.


3. **Consumo Transparente en el Cliente (`JettraStoreDriver`):**
* El cliente final invoca operaciones estándar (como `findAll()` o `JettraQL`) esperando una respuesta unificada o perezosa. El driver debe encargarse internamente de consumir el stream de chunks proveniente de **JettraStore**.
* El driver debe ensamblar o disponibilizar los datos de manera eficiente (acumulándolos progresivamente o entregándolos bajo demanda) para proteger el Heap del cliente final.


4. **Adaptación UX en Interfaces (`JettraShell` y `JettraStoreFX`):**
* **JettraShell:** Al dispararse el Sentinel, debe imprimir en la consola el aviso correspondiente y renderizar la llegada de los datos de forma progresiva o paginada para no saturar el búfer de la terminal.
* **JettraStoreFX:** Al recibir la notificación del evento, debe mostrar un indicador visual sutil (toast/barra de estado) al usuario informando que la consulta masiva se está optimizando, y alimentar los componentes visuales (`TableView` o modelos virtuales) mediante la recepción incremental del stream para mantener la fluidez de la interfaz.
